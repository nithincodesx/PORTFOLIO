3. CMS ARCHITECTURE (how content works — the core system)
--------------------------------------------------------------------------------
One Firestore document holds everything:  collection "siteConfig", doc id "main".
SiteConfig top-level keys (lib/cms/types.ts):
  hero        headline{line1,line2,line3,accent}, description, primaryCta, secondaryCta
  about       {headline, body}            ← EDITABLE BUT NOT RENDERED ON THE SITE
  projects    label, number, allProjectsLabel/Href, items[{num,title,tags,year,url,desc}]
  gallery     enabled, label, title, hint
  services    label, number, items[{icon,title,desc}]
  experience  label, number, items[{period,role,company,location,stack,summary?}]
  skills      items[{name,level}]         ← EDITABLE BUT NOT RENDERED ON THE SITE
  socials     items[{label,href}]
  contact     label, headline[], email, messageLabel, cvLabel, resumeUrl
  content     marquee[], footer{logo,copyright,credit}
  theme       accent, accentDim, bg, surface   (fed into CSS variables live)
  music       enabled, src, label, defaultVolume, loop, autoplay
  sections    SectionEntry[{id,label,visible,order,dividerAfter}] ← homepage order/visibility

Data flow (three layers, always safe):
  1) Server: app/layout.tsx → getSiteConfigServer() (Firestore REST, ISR 60s)
     → merged over DEFAULT_SITE_CONFIG → passed as initialConfig.
     So the SSR HTML already contains CMS content even if the browser fetch fails.
  2) Client: SiteConfigProvider subscribes via onSnapshot → live updates.
  3) Fallback: any failure → DEFAULT_SITE_CONFIG. The site NEVER breaks or looks
     half-empty.

Saving: each editor calls saveSection(topLevelKey, value) → setDoc(..., {merge:true}).
Only its own key is written (partial merge — editors never clobber each other).

Registered editors (lib/cms/registry.tsx):
  Content:   hero, projects, gallery, services, experience, contact, content,
             about [badge: "Not on site yet"], skills [badge: "Not on site yet"]
  Settings:  theme, music
  Structure: sections (custom visibility/order editor)

Security:
  - firestore.rules: read if true; create/update/delete only when
    request.auth.token.email is in ['shulk6339@gmail.com']; everything else denied.
  - NEXT_PUBLIC_ADMIN_EMAILS must stay in sync with the rules
    (currently shulk6339@gmail.com).
  - /control is noindex + disallowed in robots.txt; the guard still verifies a
    real Firebase session + allowlist.
  - GITHUB_TOKEN (if ever added) must be SERVER-ONLY — never NEXT_PUBLIC_.
